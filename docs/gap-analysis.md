## Master table inventory and UI coverage

There are **16 application-owned `_mst` tables** in the current migration history. V18 renamed legacy table names to the `_mst` convention; the table listed here is the current application name. `legacy_cabin_zones_archive` was removed by V23 and is not a current master. The two relationship tables are intentionally managed through their owning screens, rather than presented as duplicate standalone CRUD modules.

All organization-managed configuration endpoints require a validated principal, an active membership, and `ADMINISTER_ORGANIZATION`; tenant-owned queries and mutations receive the organization ID from that server-resolved principal. The common configuration controller provides GET list/table/export/template and POST save/import/activate/deactivate routes where a resource supports them. The table screen uses server-side search, paging (maximum 100), status filtering and sorting, plus XLSX export. CSV import is staged, validated, then committed through POST; it is not available for every resource. Supported configuration changes are written through the existing append-only configuration audit event path. Role/permission and menu visibility remains backend-enforced.

### Navigation and operational configuration adjacent to masters

`operational_forms_dtl` and `operational_form_versions_dtl` are not `_mst` tables, but Form Master is a required Administration resource. It has a dedicated version-aware UI and `/api/v1/configuration/forms` APIs rather than generic CRUD; draft editing, immutable published versions, area/purpose/stage mapping, publication validation, preview and status actions are preserved. Defect forms, versioned submissions, team assignment, and workflow records remain domain modules, not master screens. Reviewer routing is also a dedicated protected configuration editor and has a backend POST operation with a reason.

### Multi-area form mapping (V38)

Form Master now permits one form definition to be mapped to multiple active areas within its tenant. `operational_form_areas_mst` is the mutable parent mapping and is backfilled from each existing form's `area_id`. `operational_form_version_areas_dtl` captures the areas for each version and is backfilled from the stored version `area_id`; published-version snapshots are protected by a database trigger. The legacy `area_id` columns remain for compatibility and identify the primary area, but reporting and existing-defect form resolution use version-specific area snapshots. `GET /api/v1/configuration/form-mappings?formId={id}` returns supported area/purpose/stage choices with current mapping flags; `POST /api/v1/configuration/forms/{id}/mapping` takes the complete `areaIds` list, purpose, workflow stage, and reason. Saving remapping creates or updates a draft snapshot; it does not alter a published version's availability before republishing. Create and duplicate also accept `areaIds`. Backend validation checks active tenant ownership, supported purpose/stage combinations, and area-specific publication rules. All report, form options, attachment, maintenance-action, and closure-form paths resolve the published snapshot against the actual selected/defect area.

The common configuration UI consumes backend-provided menu entries and renders a section selector only for definitions returned by that API. API Rate Limits is a separate page rendered from the effective navigation key; it is not a duplicate generic table. All menu entries remain filtered by backend permissions, and direct protected API calls remain permission-checked. Existing organization onboarding provisions its own Organization and menu; V33 adds the area-team mapping submenu through the same onboarding trigger pattern and adds no permission grants.

### Area-to-maintenance routing (V33)

V33 adds `area_maintenance_team_mappings_mst`, immutable `defect_workflow_versions_dtl`, and a tenant pointer in `defect_workflow_config_mst`; `defects_dtl.workflow_version_id` snapshots the applicable workflow version when each new defect is created. Existing organizations are initialized to `REVIEWER_APPROVAL`, preserving the current Reviewer routing behavior. Administrators can explicitly create a new version using `DIRECT_MAINTENANCE`; existing defects retain their previous version and are not rerouted by a configuration change. The migration provisions the Administration submenu for current and newly provisioned organizations and does not change role grants.

The dedicated `AreaTeamRoutingPage` manages tenant-owned area/team mappings and displays open direct-assignment exceptions plus append-only reason/actor/time history. Backend endpoints are under `/api/v1/configuration/area-team-routing`; every read and mutation requires `ADMINISTER_ORGANIZATION`, and tenant identity comes only from the validated principal. A mapping must target an active tenant cabin area and active `MAINTENANCE` team with an active member whose effective role grants `PERFORM_ACTION`. A partial unique index permits only one active team mapping for an area. `ConfigurationService` prevents deactivating a Maintenance team while it has an active mapping.

In Reviewer mode, new defects continue to be created as `REPORTED` and notify the eligible Reviewer team. In direct mode, a valid mapping creates the defect and its ordinary `corrective_actions_dtl` assignment in the same transaction, moves the case to `ACTION_ASSIGNED`, records `REPORTED` and `AREA_MAINTENANCE_ROUTED` audit events, and sends existing team notifications. Missing/ineligible mapping never selects an arbitrary team: the defect remains `REPORTED`, unassigned and appears in the administrator exception queue. After fixing the mapping, an authorized administrator may invoke the safe retry endpoint; defect-row locking and active-action checks prevent duplicate assignments. No new workflow engine or permission is introduced.

### Galley Reviewer Decision Form (2026-10-14)

The existing `REVIEW_DECISION` purpose is resolved for Galley cases in the actual supported stages `REPORTED` and `UNDER_REVIEW`; `REVIEWER` is not a `WorkflowStage` in this checkout. Form Master now requires exactly four approved bindings: Decision (required `REVIEW_DECISIONS` dropdown), Assign Team (required `MAINTENANCE_TEAMS` dropdown visible only when Decision equals `APPROVE`), Rejection Reason (required textarea up to 2,000 characters visible only when Decision equals `REJECT`), and optional Remark (textarea up to 2,000 characters). Conditional configuration is data-only `{fieldKey, equals}` and publication validation accepts only these approved decision rules.

The workflow API still accepts typed `decision`, `maintenanceTeamId`, `rejectionReason`, `remark`, `formId`, and `versionId`. The server requires a rejection reason for REJECT, rejects a team with REJECT, requires and revalidates an active eligible same-tenant Maintenance team with APPROVE, checks the current published version and routed Reviewer under the existing defect-row lock, and records the reason/remark/form version/actor in the append-only event. Approval still stops at `INSPECTION_REQUIRED`; inspection completion creates the maintenance assignment. No form submission JSON or new table is used for the decision. The opt-in local demo seed adds only a seed-owned Galley decision draft to the synthetic demo tenant when none exists; the smoke test publishes it through `OperationalFormService`. Existing manual forms and published versions remain untouched. No migration was needed because the definition is existing versioned form configuration and the decision is recorded through the existing workflow event.

### Maintenance Action form and SLA date policies (2026-10-14)

V34 adds tenant-scoped `maintenance_sla_policies_mst` and permits `ON_HOLD` in the existing `corrective_actions_dtl.status` constraint. It reuses `corrective_actions_dtl.due_at` as the SLA target date and synchronizes the existing `defects_dtl.due_at` projection; no new SLA date column, answer table, alert worker, or notification was added. Existing and future organizations receive WIP=15 future calendar days, On Hold=180, and an unconfigured Close Submitted policy. Past dates are initially disabled. Organization administrators can configure whether a date is required, bounded past/future dates and the business timezone under Administration → Maintenance SLA Policies. Updates require a reason, are read from the database on each applicable request, and create before/after append-only `defect_events_dtl` events.

The opt-in development seed adds `Galley Maintenance Action (DEMO)` only if its seed-owned form key does not already exist. Its three fields are required Maintenance Status, required SLA Target Date, and optional Remarks (maximum 2,000 characters). The smoke-test path publishes a seed-owned draft through `OperationalFormService`; it does not directly insert a published version or overwrite administrator configuration. Non-demo tenants must create/configure/publish a `CORRECTIVE_ACTION` form through Form Master.

Corrective-action form resolution is limited to the defect's area, current eligible workflow stage, tenant, active assignment and published version. The effective-policy GET is scoped to the assigned active maintenance user/team. The POST maintenance-form endpoint requires `PERFORM_ACTION`, tenant-visible defect access, active assigned-team membership or the existing individual assignment, active corrective action, exact current published form/version and server-side status/date validation. It locks the action and defect. WIP maps to action `IN_PROGRESS`; On Hold maps to `ON_HOLD` after work has started; Close Submitted completes the corrective action and moves the defect only to `AWAITING_VERIFICATION`. It never directly closes the defect. Verification failure or rejected closure returns the work to the maintenance queue while preserving the decision event. SLA pause/resume and notifications/alerts are not implemented.

## Authentication evidence in this repository

- Spring Security is stateless and uses Spring's default Bearer-token resolver (`Authorization: Bearer …`).
- `SecurityConfig` constructs a `NimbusJwtDecoder` from `SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_ISSUER_URI`, applies issuer/time validation, and adds an `OAUTH2_AUDIENCE` check.
- The original `DefectController` read `operator_id` and `sub` from the validated JWT and checked `scope`/`scp`-derived `SCOPE_defects.read` and `SCOPE_defects.write`. It has been changed to resolve `operator_id` + `sub` against active `operator_memberships`; the application role is from that DB record and backend permission checks gate each operation.
- Production browser integration expects `window.eCabinAuth.getAccessToken()`; no enterprise gateway adapter, gateway headers, Microsoft integration, role/group claim mapping, user directory, or user provisioning exists in this repository. A separate loopback-only `local-auth` profile issues short-lived tokens for the seeded `abc@gmail.com` demo membership and is not evidence of the real gateway contract.
- No signing algorithm is pinned in application configuration; Spring Nimbus validates the token signature using issuer metadata/JWKS. Issuer/JWKS and forwarded-header behavior therefore remain unknown until the gateway contract is supplied.

No claim about Microsoft token type, exact signing algorithm, issuer, audience, key-rotation behavior or gateway headers can be made from this repository. Spring Resource Server's current default expects a JWT bearer token using issuer discovery/JWKS. The actual enterprise gateway owner must validate that this is their supported interface.

## Gap severity

# Form Master lifecycle actions and version mapping snapshots — 2026-10-14

Form Master exposes the existing draft editor and version workflow alongside Duplicate, Rename, Remap, Delete, Activate/Deactivate, and View Published Version in a responsive per-row actions dialog. These endpoints remain tenant-scoped and require `ADMINISTER_ORGANIZATION` at the backend. Mutations that affect configuration require an audit reason and record the validated actor through the append-only event path.

`POST /api/v1/configuration/forms/{sourceFormId}/duplicate` creates a separate form and DRAFT version transactionally. It defaults to the source's current published version; an available version can be explicitly selected. Unpublished work is never silently chosen, and copies do not include defects, submissions, evidence, audit data, or publication state. Rename updates current form metadata and a draft snapshot while leaving published version names intact. `GET /api/v1/configuration/form-mappings` returns active-tenant area/purpose/stage options supported by backend rules; Reviewer Decision choices are limited to Galley; Closure Approval choices are available for every active tenant cabin area at `APPROVAL_REQUIRED`. Remap creates or updates a draft snapshot, preserving the published version's original area/purpose/stage/name. Permanent deletion is allowed only when a form has never been published and has no submission, attachment, or defect-workflow references; drafts are deleted before their parent, and the delete event retains the removed form's identifiers and reason. Deactivation is blocked when it would leave active cases without an alternate published form for the relevant mapping.

Flyway V37 adds immutable version mapping/name snapshot fields, a tenant area foreign key, mapping constraint and index. Existing rows are backfilled from their parent form during migration; the published-version immutability trigger is disabled only around that transactional metadata backfill and immediately re-enabled. A before-insert snapshot trigger keeps legacy SQL demo-seed inserts compatible. The opt-in PostgreSQL smoke test expects 37 migrations and checks the V37 columns/trigger. Database execution of V37 is reported only if the configured local PostgreSQL verification actually runs.
